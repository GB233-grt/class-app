# 数据库与迁移

数据库跑在 Supabase 托管的 PostgreSQL 上，**所有脚本都在 SQL Editor 里手动执行**，没有自动迁移工具。

---

## 表结构总览

| 表 | 作用 | 关键约束 |
| --- | --- | --- |
| `students` | 学生 / 教师 / 管理员资料 | `email` 唯一；`points >= 0` |
| `items` | 商品 | `cost >= 0`（0 = 免费）；`stock >= 0`；`type in (physical, digital)` |
| `redemptions` | 兑换记录 | 保存商品名与单价**快照**；`item_id` 外键 `RESTRICT` |
| `points_ledger` | 积分明细 | 每笔加/扣分一条，含 `balance_after` |
| `system_settings` | 系统配置键值对 | `key` 主键；值存 JSON 字符串 |

查看各表结构：

```sql
select table_name, column_name, data_type, is_nullable
from information_schema.columns
where table_schema = 'public'
order by table_name, ordinal_position;
```

## 全新数据库

在 Supabase **SQL Editor** 里按顺序执行：

```text
database/all-in-one/step1-schema.sql     -- 建表 + 原子函数 + RLS
database/all-in-one/step2-seed.sql       -- 示例数据
```

验收：

```sql
-- 应返回 5 张表
select count(*) from information_schema.tables
where table_schema = 'public'
  and table_name in ('students','items','redemptions','points_ledger','system_settings');

-- 应返回 3 个函数
select proname from pg_proc
where pronamespace = 'public'::regnamespace
  and proname in ('adjust_student_points','redeem_item','expire_items');
```

判断某个脚本是否执行过：

```sql
-- 11 之前：items.cost 约束是 cost > 0
-- 13 之后：约束变成 cost >= 0
select conname, pg_get_constraintdef(oid)
from pg_constraint
where conrelid = 'items'::regclass and conname = 'items_cost_check';

-- 14 之后：items 才有 expires_at 列
select column_name
from information_schema.columns
where table_name = 'items' and column_name = 'expires_at';
```

## 核心函数

积分与库存的写操作全部封装在数据库函数里，单事务原子完成。

### `adjust_student_points(p_student_id, p_delta, p_reason, p_actor_id)`

锁定学生行 → 校验余额 → 更新余额 → 写积分明细。
扣分超过余额时抛异常，整笔回滚。

### `redeem_item(p_student_id, p_item_id, p_quantity)`

锁定商品行 → 校验上架 / 库存 / 积分 → 扣积分扣库存 → 写兑换记录（**商品名与单价快照**）→ 写积分明细。

- 实物商品：记录状态 `pending`，等教师发放
- 网络商品：记录状态 `fulfilled`，写入 `download_url`
- 0 积分商品：不扣分、不写积分明细，但仍扣库存

### `expire_items()`

把 `expires_at` 已过的上架商品批量下架，返回本次下架数量。
惰性清理：`GET /api/items` 与 `POST /api/redemptions` 都会先调用它一次。

## 跑数据库测试

`database/tests/redeem_item.test.sql` 覆盖 5 个场景，**全程在一个事务里，最后 ROLLBACK**，不会留下测试数据。

执行：复制整个文件 → Supabase **SQL Editor** → Run。

预期输出（只有这两行，没有红色报错）：

```text
DO
ROLLBACK
```

失败时会看到形如：

```text
ERROR:  场景2失败：网络商品兑换后库存应为 0，实际 1
```

说明当前数据库的 `redeem_item` 不是最新版本 —— 检查是否漏执行了 `13_allow_zero_cost_items.sql`。

覆盖的场景：

| 场景 | 断言 |
| --- | --- |
| 实物兑换 | 余额 −5、库存 −1、状态为 `pending` |
| 网络兑换 | 余额 −5、库存 −1、状态为 `fulfilled`、写入下载链接、积分明细 +1 |
| 库存不足 | 抛「库存不足」，余额不变 |
| 积分不足 | 抛「积分不足」 |
| 0 积分商品 | 余额不变、库存 −1、积分明细不新增 |

## 备份与恢复

Supabase 免费版提供每日备份（可在控制台 **Database → Backups** 查看）。
需要手动导出时，用本机 `pg_dump`（连接串在 **Project Settings → Database**，含数据库密码，**不要贴到任何文档里**）：

```bash
# 只导出结构与数据（不含 auth schema）
pg_dump "postgresql://postgres:<DB_PASSWORD>@db.<project>.supabase.co:5432/postgres" \
  --schema=public \
  --no-owner \
  -f backup_$(date +%Y%m%d).sql
```

恢复：

```bash
psql "postgresql://postgres:<DB_PASSWORD>@db.<project>.supabase.co:5432/postgres" -f backup_20250101.sql
```

> `auth.users`（登录账号）不在备份范围内，它由 Supabase Auth 管理。恢复后可能需要重新创建账号，再用 seed 脚本对齐 `students.id`。

## 改表结构的规则

1. **只增不改**：已发布的迁移脚本不要修改，新增 `NN+1_xxx.sql`
2. 脚本必须可重复执行：`IF NOT EXISTS` / `DROP POLICY IF EXISTS` / `CREATE OR REPLACE`
3. 同步更新 `database/all-in-one/step1-schema.sql`，保证「全新安装」和「增量升级」结果一致
4. 改了函数就在 [[数据库与迁移#跑数据库测试]] 里补场景
